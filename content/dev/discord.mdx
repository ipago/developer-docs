---
title: Discord roles
description: Sell roles on your Discord server. iPago's bot grants them when an order is paid and takes them back when access ends.
---

A package can grant roles on your Discord server. The buyer links their Discord
account before paying, and iPago's bot gives them the roles as soon as the order
is paid. It takes them back when the access ends: a subscription stops, or the
order is fully refunded or charged back.

A package can do this on its own or next to its other delivery: a VIP package
can run a rank command on your game server and grant a VIP role on Discord.

iPago runs one Discord bot for every store, so there is nothing to host. Discord
roles are available once the iPago server you use has Discord set up; the panel
says so under **Integration → Discord** when it does not.

## Connect your server

1. Open **Integration → Discord** in the panel and press **Connect Discord server**.
2. Discord asks you to pick a server and to let iPago's bot manage roles. You need
   the **Manage Server** permission on that server to add a bot to it.
3. You come back to the panel with the server connected.

Each store connects one server per mode: test mode has its own connection, so you
can try the whole flow on a test server before selling on your real one.
**Disconnect** stops new grants. Roles already given stay where they are, and
removals already queued (a refund, an ended subscription) still run.

<Callout type="warn">
Discord only lets a bot hand out roles **below its own highest role**. After
connecting, open your server's role list and drag the **iPago** role above every
role you want to sell. It also needs the **Manage Roles** permission, which the
invite asks for. Roles at or above the bot's role, `@everyone`, and roles another
integration manages (bot roles, the booster role) cannot be granted, and the panel
shows them greyed out with the reason.
</Callout>

## Add roles to a package

Edit a package in **Catalog** and tick up to **10 roles** under **Discord roles**.
The list comes from your connected server. Saving checks every role against it: a
role that does not exist or that the bot cannot grant is refused with the reason.

Through the API, the roles live in the package's `delivery_config` next to any
game commands:

```json
{
  "commands": [{ "kind": "online", "command": "lp user {username} parent add vip" }],
  "discord": { "roles": ["1234567890123456789"] }
}
```

Role ids are Discord's: 17 to 20 digits, as Discord's developer mode copies them.

## How buyers link Discord

On your iPago storefront this is handled for you. When something in the basket
(or a subscription being bought) grants Discord roles, the basket and checkout
show **Link your Discord account**. The buyer authorizes iPago on Discord's own
screen and comes back with their account shown, and a **Change** link to pick
another. Checkout refuses to start until an account is linked.

Linking asks Discord for two things: who the buyer is (`identify`), and permission
for the bot to add them to your server (`guilds.join`), since a role can only be
given to a member. A buyer who is not in your server yet is added at that moment.
iPago uses the buyer's Discord access token for exactly those two calls and does
not keep it; what it keeps is the Discord user id (and the username, to show you
who it was) on the order.

Building your own storefront on the [Storefront API](/dev/storefront/overview)?
The same flow, step by step:

1. `POST /v1/storefront/{slug}/discord/authorize` with a `return_url` on your
   storefront's host. Send the buyer to the `url` it returns.
2. Discord sends the buyer, through iPago, back to `return_url` with
   `discord_link=<token>` added to the query, or `discord_error=<code>` when it did
   not work (`access_denied` when they cancelled).
3. Keep the token (it is valid for 24 hours) and send it as `discord_link` when you
   [check out the basket](/dev/reference/baskets#check-out-a-basket) or
   [start a subscription](/dev/reference/baskets#start-a-subscription-checkout).

Baskets and storefront products carry `requires_discord: true` when they need it.

## Developer API: `discord_user_id`

[`POST /v1/checkouts`](/dev/reference/checkouts#create-a-checkout) takes the buyer's
Discord user id directly, for integrations that link Discord themselves:

```bash
curl -X POST https://api.ipago.io/v1/checkouts \
  -H "Authorization: Bearer sk_test_..." \
  -H "Idempotency-Key: 8d0f3c4e-1a2b-4c5d-9e8f-0a1b2c3d4e5f" \
  -H "Content-Type: application/json" \
  -d '{ "items": [{ "product": "prod_01M5MWGB718BWKF7MDP3BX63TY" }],
        "discord_user_id": "1234567890123456789", "withdrawal_waiver": true }'
```

| Field | Required | Description |
| --- | --- | --- |
| `discord_user_id` | when any item grants Discord roles | The buyer's Discord user id, 17 to 20 digits. Get it from your own Discord OAuth2 login (scope `identify`), so it really is the buyer's. For a subscription it is kept for every renewal. |

iPago does not add the buyer to your server on this path. Make sure they have
joined it (or join them yourself with `guilds.join`) before the order is paid, or
the grant fails with "The buyer is not a member of the Discord server".

The id comes back as `discord_user_id` on the [order](/dev/reference/orders) and on
the subscription.

## Errors at checkout

| Code | Status | Meaning |
| --- | --- | --- |
| `discord_link_required` | 400 | An item grants Discord roles and no Discord account was given, or the link token expired or belongs to another store. `param` names the field: `discord_link` or `discord_user_id`. |
| `discord_not_connected` | 400 | The store has no Discord server connected in this mode, so the roles could not be delivered. Nothing is charged. |
| `discord_not_configured` | 503 | Discord is not set up on this iPago server. |

## When roles are granted and taken back

| Event | What happens |
| --- | --- |
| Order paid (and every subscription renewal) | Each role is granted. The delivery completes once every role, and every game command of the same package, is done. |
| Subscription ends | Every role its periods granted is removed. |
| Order fully refunded | Its roles are removed. A partial refund keeps them. |
| Dispute lost | Its roles are removed. |

A role is only removed when **no other purchase** still pays for it: a buyer who
bought VIP twice and refunded one keeps VIP. Grants and removals are idempotent,
so a repeated webhook never grants or removes twice.

Discord being down, or rate limiting the bot, delays a grant rather than losing
it: it is retried on the same schedule as [webhooks](/dev/webhooks/overview), for
about a day and a half. A permanent answer fails the delivery straight away with
the reason, which you see on the order in the panel and in the `delivery.failed`
event's `note`:

| Reason | Fix |
| --- | --- |
| The buyer is not a member of the Discord server. | Ask them to join, then fulfil the order by hand. |
| iPago's bot is not allowed to manage this role. | Give the bot's role **Manage Roles** and move it above the role. |
| The Discord role no longer exists. | Pick a current role on the package. |
| iPago's bot is no longer in the Discord server. | Reconnect the server under **Integration → Discord**. |
