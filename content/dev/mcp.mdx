The iPago MCP server lets an AI assistant read the iPago documentation and call the
[Developer API](/dev/developer-api/overview) against your **test-mode** store, from inside the tools
you already use.

| | |
| --- | --- |
| Server URL | `https://mcp.ipago.io/mcp` |
| Transport | Streamable HTTP, stateless. Requests are `POST` only. |
| Authentication | `Authorization: Bearer sk_test_...` header |

Without a key the server still works, but only the two documentation tools are available.
With a test key you also get the API tools below. A restricted test key (`rk_test_...`) works
too: the API tools then can do only what that key's scopes allow.

If you send an `Authorization` header that is not a valid key, the server answers HTTP 401 with a
JSON-RPC error (code `-32001`) instead of falling back to the documentation tools. That covers a
typo in the key, a publishable key (`pk_...`), and any scheme other than `Bearer`. Leave the
header out entirely if you only want the documentation tools.

## Test keys only

<Callout type="warn">
  The hosted server refuses live keys (`sk_live_...` and `rk_live_...`). A request with a live
  key gets a JSON-RPC error and no tools. Use a `sk_test_` key from the panel with the page
  switched to **Test**.
</Callout>

An assistant can call tools on its own, and a misread instruction should never move real money.
A test key only touches [test-mode](/dev/developer-api/test-mode) data, so the worst case is a
test order you can ignore. For the same reason, `create_refund` is never offered for a live key.

## Tools

The documentation tools work with or without a key. A trailing `?` marks an optional parameter.

| Tool | Parameters | What it does |
| --- | --- | --- |
| `search_docs` | `query` | Searches the iPago documentation and returns matching pages with url, title and excerpt. |
| `get_doc_page` | `slug` | Returns the full markdown of one documentation page, given its slug: the path of a `search_docs` result URL after the domain, e.g. `https://docs.ipago.io/dev/checkout/overview` gives `dev/checkout/overview`. Only `dev/...` and `creators/...` slugs are accepted. |

The API tools need a `sk_test_` key. Every list tool also takes `limit?` (1 to 100) and
`starting_after?`, listed below only where it has extra filters.

| Tool | Parameters | What it does |
| --- | --- | --- |
| `list_products` | `limit?`, `starting_after?`, `active?` (`true` or `false`), `category?` (category id) | Returns a page of the store's products with prices. |
| `get_product` | `id` | Returns one product by id. |
| `create_checkout` | `items` (array of `{product, quantity?}`), `customer_email?`, `country?` (2-letter code) | Creates a checkout session for the given products and returns it, including the hosted payment URL. |
| `list_orders` | `limit?`, `starting_after?`, `status?` | Returns a page of orders. |
| `get_order` | `id` | Returns one order by id. |
| `get_balance` | none | Calls `GET /v1/balance` and returns that payload. The tool name stays until the ledger change. It is not the weekly invoice. |
| `list_deliveries` | `limit?`, `starting_after?`, `status?` | Returns a page of fulfilment deliveries. |
| `list_events` | `limit?`, `starting_after?` | Returns a page of API events. |
| `get_event` | `id` | Returns one API event by id. |
| `list_webhook_endpoints` | `limit?`, `starting_after?` | Returns a page of webhook endpoints. |
| `create_webhook_endpoint` | `url`, `events?` (array of event names) | Creates a webhook endpoint and returns it including its signing secret, which is shown once and cannot be retrieved later. |
| `send_test_event` | `endpoint_id` | Sends a test event to a webhook endpoint and returns the delivery result. |
| `list_refunds` | `limit?`, `starting_after?`, `status?` | Returns a page of refunds. |
| `list_disputes` | `limit?`, `starting_after?`, `status?` | Returns a page of disputes. |
| `list_payouts` | `limit?`, `starting_after?`, `status?` | Returns a page of `payout` objects from `GET /v1/payouts`. The tool name stays until the ledger change. |
| `create_refund` | `order`, `reason?` | Refunds an order and returns the refund. Test mode only. |

`starting_after` is the id of the last object of the previous page. The documentation tools read the same content as
[`llms-full.txt`](https://docs.ipago.io/llms-full.txt) and `/md/<slug>` pages described in
[Build with AI](/dev/build-with-ai).

`create_webhook_endpoint` returns the signing secret once. Ask your assistant to store it in
your environment configuration straight away rather than repeating it in the chat.

## Set up your client

Replace `sk_test_...` with your test key in each example.

### Claude Code

```bash
claude mcp add --transport http iPago https://mcp.ipago.io/mcp \
  --header "Authorization: Bearer sk_test_..."
```

Add `--scope project` to share the server with your team through `.mcp.json`. If you do, keep
the key out of the file: reference an environment variable instead, as
`"Authorization": "Bearer ${IPAGO_TEST_KEY}"` in the `headers` object.

### Cursor

Create `.cursor/mcp.json` in your project, or `~/.cursor/mcp.json` for all projects:

```json
{
  "mcpServers": {
    "iPago": {
      "url": "https://mcp.ipago.io/mcp",
      "headers": {
        "Authorization": "Bearer ${env:IPAGO_TEST_KEY}"
      }
    }
  }
}
```

Cursor reads `IPAGO_TEST_KEY` from your environment, so the key never lands in a file you
might commit.

### VS Code

Create `.vscode/mcp.json`. VS Code asks for the key the first time the server starts and
stores it securely:

```json
{
  "inputs": [
    {
      "type": "promptString",
      "id": "ipago-test-key",
      "description": "iPago test key (sk_test_...)",
      "password": true
    }
  ],
  "servers": {
    "iPago": {
      "type": "http",
      "url": "https://mcp.ipago.io/mcp",
      "headers": {
        "Authorization": "Bearer ${input:ipago-test-key}"
      }
    }
  }
}
```

### Claude Desktop and claude.ai

Open **Customize**, then **Connectors**, choose **Add custom connector**, and enter:

- Name: `iPago`
- URL: `https://mcp.ipago.io/mcp`

iPago does not offer OAuth sign-in yet, so choose no sign-in. In the **Request headers**
section add the header `Authorization` with the value `Bearer sk_test_...`. Claude sends it on
every request and stores it encrypted. Custom connectors are available on Pro, Max, Team and
Enterprise plans. On Team and Enterprise, everyone who uses the connector shares the same
credential, so use a test key.

If you leave the header out, the connector connects but only the two documentation tools are
available.

## Keep your keys safe

<Callout type="warn">
  Store the test key in the client's config, a secret prompt or an environment variable. Never
  paste it into a chat message or commit it to a repository. A key typed into a chat becomes part
  of the conversation history.
</Callout>

If a key leaks, revoke it in the panel and create a new one. See
[Authentication](/dev/developer-api/authentication#creating-and-rotating-keys).

## Try it

Once connected, ask your assistant:

```text
Use the iPago tools. List my test products, create a checkout for the first one, and show me
the payment URL. Then send a test event to my webhook endpoint.
```
