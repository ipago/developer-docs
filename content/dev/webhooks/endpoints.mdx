title: Endpoints

A **webhook endpoint** is a public HTTPS URL you own, plus the list of event
types you want delivered to it and a signing secret. You can run several
endpoints, for example one for fulfillment and one for analytics, each subscribed
to a different set of events.

## Registering an endpoint

In the panel, open **Integration → Webhooks**, choose **Add endpoint**, paste
your URL, pick the [event types](/dev/webhooks/events) you want (or all of
them), and save.

You can also create endpoints over the Developer API with a key that has the
`webhooks:write` scope. The body is JSON:

```bash
curl https://api.2pay.gg/v1/webhook_endpoints \
  -H "Authorization: Bearer sk_live_..." \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{
    "url": "https://example.com/hooks/2pay",
    "events": ["order.paid", "delivery.pending"]
  }'
```

The response (`201 Created`) includes the endpoint's **signing secret**. It is
returned this once and never again:

```json
{
  "object": "webhook_endpoint",
  "id": "we_01JB7R0D4F7H2K5M8P1S4V7Y0B",
  "url": "https://example.com/hooks/2pay",
  "events": ["order.paid", "delivery.pending"],
  "status": "active",
  "created": "2026-06-28T12:00:00.000Z",
  "secret": "whsec_example"
}
```

| Field | Description |
| --- | --- |
| `id` | Endpoint id (`we_`). |
| `url` | Where events are delivered. Must be `https`, and must not point at `localhost`, a private, loopback, link-local or CGNAT address, or the cloud metadata address. Anything else is refused with `400 invalid_url`. |
| `events` | The subscribed event types. Omit the field, or send `["*"]`, to receive every current and future type. An empty array is refused with `400 invalid_events`. |
| `status` | `active` or `disabled`. A new endpoint is `active` immediately and starts receiving events. |
| `secret` | The key used to [sign](/dev/webhooks/verifying-signatures) each request, prefixed `whsec_`. Store it now; it is not retrievable later. |

<Callout type="warn">
  Store the `secret` immediately and treat it like a password. It is how you
  prove a delivery is genuinely from 2Pay. If it leaks,
  [rotate it](#rotating-the-signing-secret) and update your handler.
</Callout>

<Callout type="info">
  The panel only lets you pick types from the catalog. The Developer API route
  does not check the names you send, so a typo such as `order.payed` is saved
  and simply never matches anything. Copy type names from
  [Events](/dev/webhooks/events).
</Callout>

## Managing endpoints

The Developer API covers create, read and delete:

```
POST   /v1/webhook_endpoints             # create          (webhooks:write)
GET    /v1/webhook_endpoints             # list            (webhooks:read)
GET    /v1/webhook_endpoints/{id}        # retrieve        (webhooks:read)
DELETE /v1/webhook_endpoints/{id}        # remove          (webhooks:write)
POST   /v1/webhook_endpoints/{id}/test   # send a test     (webhooks:write)
```

```bash
curl https://api.2pay.gg/v1/webhook_endpoints \
  -H "Authorization: Bearer sk_live_..."
```

The list is [paginated](/dev/developer-api/pagination) like every other list.
Retrieving or listing never returns the secret.

Deleting returns `{ "object": "webhook_endpoint", "id": "we_...", "deleted": true }`.
It stops delivery to that URL immediately and removes the endpoint's delivery
history with it.

To change an endpoint's URL or events, or to switch it off
without deleting it, edit it in the panel under **Integration → Webhooks**.
Narrowing the events also applies to deliveries already queued: an event the
endpoint no longer subscribes to is dropped instead of sent.

The test route is covered in
[Delivery & testing](/dev/webhooks/delivery-and-testing#from-the-developer-api).

## Disabled endpoints

An endpoint is `disabled` either because you switched it off in the panel or
because 2Pay gave up on it: when one delivery fails all 15
[attempts](/dev/webhooks/delivery-and-testing#retries), the endpoint is
disabled so a dead URL does not pile up a queue. Its remaining queued deliveries
are marked failed, and no new events are queued for it.

Re-enable it in the panel once your receiver is fixed, then backfill the gap
from the [Events API](/dev/developer-api/events#catching-up-after-downtime).

## Rotating the signing secret

In the panel, open the endpoint and choose **Rotate secret**. You get a new
`whsec_` secret, shown once.

Rotation does not cut the old secret off straight away. For the next **24
hours** every delivery is signed with **both** secrets, so the
`2Pay-Signature` header carries two `v1=` values:

```
2Pay-Signature: t=1751110929,v1=<signature with new secret>,v1=<signature with old secret>
```

That window lets you deploy the new secret to your receiver after rotating,
not in lockstep with it. It only works if your verification accepts a request
when **any** `v1` matches, which is what the samples in
[Verifying signatures](/dev/webhooks/verifying-signatures) do. After 24 hours
only the new secret signs. Rotating again during an open window replaces it, so
at most two secrets are ever live.

## Test mode vs live mode

Endpoints belong to one mode. An endpoint created with a
[test key](/dev/developer-api/authentication), or in the panel's test mode,
receives only test-mode events; a live endpoint receives only live events. Keep
separate endpoints (and ideally separate handler deployments) for the two so a
sandbox sale never hits production fulfillment.
