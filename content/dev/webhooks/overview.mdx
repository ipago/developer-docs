**Webhooks** are how iPago tells your systems that something happened, the moment
it happens: a payment cleared, an item is ready to deliver, a `payout` event fired.
Instead of polling our API on a loop, you register a URL once and iPago sends a
signed `POST` to it for each event you care about.

Webhooks are the real-time backbone of both the
[Developer API](/dev/developer-api/overview) and the
[Game API](/dev/game-api/overview): they are what wakes your fulfillment code up.

## How it works, end to end

1. You [register an endpoint](/dev/webhooks/endpoints) (a public HTTPS URL) and
   subscribe it to one or more [event types](/dev/webhooks/events), or to `*`
   for everything. It is `active` straight away; there is no handshake to
   complete.
2. Whenever a subscribed event occurs, iPago `POST`s the
   [event object](/dev/developer-api/events) to your URL as JSON, signed with
   the endpoint's secret.
3. Your server [verifies the signature](/dev/webhooks/verifying-signatures),
   acks fast with a `2xx`, and processes the event asynchronously.
4. If your endpoint is down or returns a non-`2xx`, iPago
   [retries with backoff](/dev/webhooks/delivery-and-testing#retries) for about
   a day and a half.

## The payload

Every webhook body is a standard event object, identical to what
[`GET /v1/events`](/dev/developer-api/events) returns. `data` is the resource
the event is about, serialized exactly as the API returns it:

```json
{
  "object": "event",
  "id": "evt_01JB7Q3M8T2K6V9X4C1N5R0WZD",
  "type": "delivery.completed",
  "created": "2026-06-28T11:42:11.512Z",
  "data": {
    "object": "delivery",
    "id": "del_01JB7Q2Y5H3F8D1S6A9G4K7M2P",
    "order": "ord_01JB7Q2X9N4B7C2E5F8H1J3K6L",
    "order_item": "oi_01JB7Q2X9P6Q1R4S7T0U3V6W9X",
    "product": "prod_01JA2B3C4D5E6F7G8H9J0K1M2N",
    "recipient": "Steve",
    "quantity": 1,
    "config": { "commands": [{ "kind": "offline", "command": "lp user {username} parent add vip", "delay": 0, "slots": 0, "servers": [] }] },
    "status": "completed",
    "note": "Confirmed by game server.",
    "created": "2026-06-28T11:40:02.118Z",
    "completed_at": "2026-06-28T11:42:11.498Z"
  }
}
```

Dispatch on `type`, then read `data` (its `data.object` field names the
resource kind). The full catalog of types and their payloads is in
[Events](/dev/webhooks/events).

Each request also carries `iPago-Event-Type`, `iPago-Event-Id` and
`iPago-Delivery-Id` headers, so you can route or deduplicate before parsing the
body. See [Delivery headers](/dev/webhooks/verifying-signatures#delivery-headers).

## The four rules that keep webhooks reliable

<Callout type="warn">
  These are not optional. Skipping any one of them is the usual cause of
  double-grants, missed sales, or spoofed deliveries.
</Callout>

1. **Verify every signature** before trusting a body. Anyone can `POST` to a
   public URL; the signature is what proves it was us. See
   [Verifying signatures](/dev/webhooks/verifying-signatures).
2. **Respond `2xx` quickly** and do the real work after. iPago waits at most 30
   seconds for an answer; a slower handler counts as a failure and is retried.
3. **Be idempotent.** The same event can arrive more than once (retries,
   network hiccups). Deduplicate on the event `id`, which is the same on every
   retry.
4. **Reconcile.** Webhooks are best-effort delivery of a perfect log. Periodically
   sweep the [Orders](/dev/developer-api/orders) or
   [Events](/dev/developer-api/events#catching-up-after-downtime) API to catch
   anything you missed. Events are not guaranteed to arrive in order either:
   a retried event can land after a newer one.

## Two kinds of webhook

Everything above describes **store webhooks**: endpoints you register once for
the whole store, receiving the events in the catalog. There is also an older,
narrower mechanism, the
[per-product delivery webhook](/dev/webhooks/delivery-webhook), which posts one
small payload per paid item to a URL set on the product itself.
