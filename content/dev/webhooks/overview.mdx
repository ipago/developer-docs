**Webhooks** are how 2Pay tells your systems that something happened, the moment
it happens: a payment cleared, an item is ready to deliver, an order was
refunded. Instead of polling our API on a loop, you register a URL once and 2Pay
sends a signed `POST` to it for each event you care about.

Webhooks are the real-time backbone of both the
[Developer API](/dev/developer-api/overview) and the
[Game API](/dev/game-api/overview): they are what wakes your fulfillment code up.

## How it works, end to end

1. You [register an endpoint](/dev/webhooks/endpoints) (a public HTTPS URL) and
   subscribe it to one or more event types.
2. 2Pay sends a one-time **validation request** to confirm you own the URL. Your
   endpoint must echo it back. See [Endpoints](/dev/webhooks/endpoints#validation).
3. From then on, whenever a subscribed event occurs, 2Pay `POST`s the
   [event object](/dev/developer-api/events) to your URL, signed with a secret.
4. Your server [verifies the signature](/dev/webhooks/verifying-signatures),
   acks fast with a `2xx`, and processes the event asynchronously.
5. If your endpoint is down or returns a non-`2xx`, 2Pay
   [retries with backoff](/dev/webhooks/delivery-and-testing#retries).

## The payload

Every webhook body is a standard event object, identical to what
[`GET /events`](/dev/developer-api/events) returns:

```json
{
  "object": "event",
  "id": "evt_01HA0ABC",
  "type": "order.paid",
  "created": "2026-06-28T11:42:11Z",
  "data": {
    "object": "order",
    "id": "ord_01HA0XYZ",
    "status": "paid",
    "delivery_status": "pending"
  }
}
```

Dispatch on `type`, then act on `data.object`. The full catalog of types and
their payloads is in [Events](/dev/webhooks/events).

## The four rules that keep webhooks reliable

<Callout type="warn">
  These are not optional. Skipping any one of them is the usual cause of
  double-grants, missed sales, or spoofed deliveries.
</Callout>

1. **Verify every signature** before trusting a body. Anyone can `POST` to a
   public URL; the signature is what proves it was us. See
   [Verifying signatures](/dev/webhooks/verifying-signatures).
2. **Respond `2xx` quickly** (within a few seconds) and do the real work after.
   Slow handlers get treated as failures and retried.
3. **Be idempotent.** The same event can arrive more than once (retries,
   network hiccups). Deduplicate on `event.id`.
4. **Reconcile.** Webhooks are best-effort delivery of a perfect log. Periodically
   sweep the [Orders](/dev/developer-api/orders#reconciliation-pattern) or
   [Events](/dev/developer-api/events#catching-up-after-downtime) API to catch
   anything you missed.
