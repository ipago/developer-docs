This page covers the operational side of webhooks: what counts as delivered,
what happens when delivery fails, and how to exercise your handler before going
live.

## Acknowledging a delivery

2Pay considers a webhook delivered when your endpoint returns any **`2xx`**
status (`200` to `299`). Anything else counts as a failure and is retried: a
`4xx`, a `5xx`, a connection error, or no answer within **30 seconds**. Redirects
are followed and the final response decides, but register the final URL rather
than relying on a redirect.

2Pay keeps the first 512 characters of your response body with each attempt,
which is what you see in the panel's delivery log. Returning a short error
message on failure makes debugging easier.

<Callout type="warn">
  Do your real work after acking. Acknowledge fast, push the event onto a queue
  or background job, and process it there. A handler that grants items inline
  and runs past the timeout gets retried, and risks double-processing.
</Callout>

## Retries

A failed delivery is retried with exponential backoff: the wait doubles after
every failure, starting at one minute and capped at six hours. Each delivery
gets **15 attempts** in total, spread over about **38.5 hours**. Every attempt
carries the same `2Pay-Event-Id` and `2Pay-Delivery-Id` and the same body; only
the signature timestamp `t` is new.

| Attempt | Wait after the previous attempt | Time after the first attempt |
| --- | --- | --- |
| 1 | | 0 |
| 2 | 1 min | 1 min |
| 3 | 2 min | 3 min |
| 4 | 4 min | 7 min |
| 5 | 8 min | 15 min |
| 6 | 16 min | 31 min |
| 7 | 32 min | 1 h 3 min |
| 8 | 1 h 4 min | 2 h 7 min |
| 9 | 2 h 8 min | 4 h 15 min |
| 10 | 4 h 16 min | 8 h 31 min |
| 11 | 6 h | 14 h 31 min |
| 12 | 6 h | 20 h 31 min |
| 13 | 6 h | 26 h 31 min |
| 14 | 6 h | 32 h 31 min |
| 15 | 6 h | 38 h 31 min |

The times are the earliest each attempt can go out. The delivery worker checks
for due work every few seconds, so real attempts land slightly later.

If the 15th attempt fails too, the delivery is marked `failed` and the
**endpoint is disabled**, so it stops receiving events until you re-enable it in
the panel. See [Disabled endpoints](/dev/webhooks/endpoints#disabled-endpoints).
Backfill anything you missed from the
[Events API](/dev/developer-api/events#catching-up-after-downtime).

| Behavior | Detail |
| --- | --- |
| Success | Any `2xx` within 30 seconds. |
| Retry trigger | Any other status, a timeout, or a connection error. |
| Schedule | 1 min, doubling, capped at 6 h. 15 attempts, about 38.5 h. |
| Same event | Identical body, event id and delivery id on every attempt. |
| Give-up | Delivery `failed`, endpoint disabled. |

## Sending a test event

### From the panel

Open **Integration → Webhooks**, find the endpoint, and choose **Send test
event**. 2Pay sends one signed [`endpoint.test`](/dev/webhooks/events#endpointtest)
event to that endpoint straight away, whatever it subscribes to, and shows you
the status code, the response body and how long it took. The panel waits up to
10 seconds for your answer. A test is attempted once and never retried; press the button again to resend. It is limited to 30
tests per minute.

A test uses the same headers and signature scheme as a real event, so it is the
quickest way to prove your signature check works end to end.

### From the Developer API

```
POST /v1/webhook_endpoints/{id}/test
```

```bash
curl -X POST https://api.2pay.gg/v1/webhook_endpoints/we_01JB7R0D4F7H2K5M8P1S4V7Y0B/test \
  -H "Authorization: Bearer sk_test_..."
```

Requires the `webhooks:write` scope. It records an `endpoint.test` event and
answers `202 Accepted` with that event; delivery then happens in the background
like any other event, with the normal retries:

```json
{
  "object": "event",
  "id": "evt_01JBB4F5G6H7J8K9M0N1P2Q3R4",
  "type": "endpoint.test",
  "created": "2026-06-28T12:01:00.000Z",
  "data": { "endpoint": "we_01JB7R0D4F7H2K5M8P1S4V7Y0B" }
}
```

<Callout type="warn">
  Unlike the panel button, this route does not address the endpoint in the
  path directly. The event goes to every active endpoint of the store in that
  mode whose subscription is `*`. An endpoint subscribed to a specific list of
  types does not receive it, even when it is the one named in the URL. To test
  such an endpoint, use the panel button. The id in the path must still exist,
  or the call returns `404`.
</Callout>

### Test mode

Point a [test-mode endpoint](/dev/webhooks/endpoints#test-mode-vs-live-mode) at
your staging handler and drive real sandbox purchases. You get genuine event
sequences, `order.paid` then `delivery.pending`, without moving money.

### Local development

Your endpoint must be reachable over public HTTPS, and 2Pay refuses `localhost`
and private addresses, so for local work put a tunnel in front of your machine:

```bash
# example with a tunneling tool of your choice
ngrok http 3000
# then register the https://<id>.ngrok.app/hooks/2pay URL as an endpoint
```

Register the tunnel URL as a test-mode endpoint, and trigger events with **Send
test event** or sandbox checkouts.

## A reliable consumer, in summary

1. Capture the raw body and
   [verify the signature](/dev/webhooks/verifying-signatures), accepting any
   matching `v1`.
2. Return `2xx` immediately.
3. Enqueue the event; process it in a background worker.
4. Deduplicate on the event `id`; make handlers idempotent.
5. Reconcile periodically against the
   [Events](/dev/developer-api/events) or [Orders](/dev/developer-api/orders) API.
