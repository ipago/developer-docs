The **Game API** is the runtime side of iPago: the interface your game server,
plugin, or bot talks to in order to **grant what players bought** and tell iPago
it is done. Where the [Developer API](/dev/developer-api/overview) manages and
observes your store from a backend, the Game API runs on (or right next to) the
machine that actually applies a rank, drops an item, or executes a command.

It is built around a **command queue**. iPago turns paid orders into per-player
commands; your server pulls that queue, runs each command in-game, and deletes it
to confirm. That design means your server only needs **outbound** HTTPS, no open
ports, no inbound webhooks on the game host itself.

## What it's for

- **Pull what's owed.** Ask iPago which players have purchases waiting and what to
  run for them.
- **Apply it in-game.** Give the rank, currency, crate, or run your configured
  command, whether the player is online now or offline.
- **Confirm it.** Delete completed commands so iPago marks the matching
  [delivery](/dev/developer-api/deliveries) complete and never re-sends it.

## How it relates to the rest of iPago

```
Buyer pays (Webstore / Checkout)
        │
        ▼
iPago creates an order + deliveries  ──▶  order.paid / delivery.pending webhooks
        │                                         (your backend, optional)
        ▼
iPago enqueues per-player commands
        │
        ▼
Your game server polls the Game API ──▶ runs commands ──▶ deletes them (confirm)
        │
        ▼
iPago marks deliveries completed     ──▶  delivery.completed webhook
```

You do **not** have to consume webhooks to use the Game API; polling the queue is
self-contained. Webhooks are useful when a separate backend also needs to know
about sales.

## Typical flow

1. A player buys on your [Webstore](/dev/webstores/overview) or embedded
   [Checkout](/dev/checkout/overview).
2. iPago creates the order and queues commands for the purchased products.
3. Your server [polls the queue](/dev/game-api/delivery-queue), gets the list of
   players with work waiting, and fetches their commands.
4. Your plugin runs each command (online or offline as appropriate).
5. Your server [deletes the executed commands](/dev/game-api/delivery-queue#4-confirm-execution),
   confirming delivery.

## Authentication in one line

The Game API uses a **server token** scoped to a single server of a single store,
sent in the `X-iPago-Server-Token` header. It can read and confirm that server's
queue and nothing else, which is what makes it safe to keep in a config on your
game host. Details in [Authentication](/dev/game-api/authentication).

## Use a plugin, or RCON, before writing your own

You rarely need to write this loop yourself:

- **Minecraft**: the official [plugin](/dev/game-api/plugins#minecraft)
  implements polling, execution, and confirmation.
- **Any server with RCON** (Rust, ARK, Source games, Minecraft without a
  plugin): add it in the panel with the [RCON](/dev/game-api/plugins#rcon)
  connection and iPago pushes the commands to it. Nothing to install, no token,
  and no Game API calls from your side.

Build directly against the API only for a custom integration.

## Rate limits

Each Game API endpoint allows 120 requests per minute per server token.
Polling at the pace the queue asks for (`meta.next_check`, 15 to 60 seconds)
stays well inside it. Details in
[Delivery queue](/dev/game-api/delivery-queue#rate-limits).
