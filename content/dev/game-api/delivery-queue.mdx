title: Delivery queue

The Game API hands your server work as a **command queue**. Each paid product
that targets a game server becomes one or more **commands**, run a console
command, give an item, grant a rank, tied to the player who bought it. Your
server's job is a simple loop: **poll** the queue, **run** the commands,
**delete** them to confirm.

All requests use the Game API base URL and
[server token](/dev/game-api/authentication):

```
https://game.2pay.gg/v1
X-2Pay-Server-Token: srv_live_...
```

## Online vs offline commands

Commands split into two kinds, because some deliveries need the player present
and some do not:

- **Online commands** require the player to be connected (give an item, teleport,
  open a crate). They are fetched per online player.
- **Offline commands** can run whether or not the player is connected (grant a
  permission, set a database flag, add currency). They run on a schedule
  independent of presence.

Which servers a command reaches is set per command on the package: name one or more of
your servers, or name none at all, which means every server of the store. A command with
a delay is simply withheld until it is due, so anything the queue hands you is ready to
run now.

## The loop

```
            ┌──────────────────────────────────────────┐
            ▼                                            │
  GET /queue  ──▶ due players? ──▶ for each online player:
       │                              GET /queue/online-commands/{id}
       │                              run them
       │                              DELETE /queue (their command ids)
       │
       └──▶ execute_offline_commands? ──▶ GET /queue/offline-commands
                                          run them
                                          DELETE /queue (their command ids)
```

### 1. Poll the queue

```
GET /v1/queue
```

```bash
curl https://game.2pay.gg/v1/queue \
  -H "X-2Pay-Server-Token: srv_live_..."
```

```json
{
  "object": "queue",
  "meta": {
    "execute_offline_commands": true,
    "next_check": 60,
    "more": false
  },
  "players": [
    { "id": "qp_01HA0...", "name": "Steve", "uuid": null }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `meta.execute_offline_commands` | If `true`, fetch and run [offline commands](#3-run-offline-commands) this cycle. |
| `meta.next_check` | Seconds to wait before polling again. Respect this instead of hammering the endpoint. |
| `meta.more` | `true` if there are more due players than returned in this page; poll again to drain. |
| `players` | Players who have online commands waiting, up to 100 per poll. Each has a queue id and the name captured at checkout. `uuid` is reserved and is `null` for now, so match players by name. |

### 2. Run online commands per player

For each player in `players` who is currently connected to your server:

```
GET /v1/queue/online-commands/{playerId}
```

```bash
curl https://game.2pay.gg/v1/queue/online-commands/qp_01HA0... \
  -H "X-2Pay-Server-Token: srv_live_..."
```

```json
{
  "object": "command_list",
  "player": { "id": "qp_01HA0...", "name": "Steve", "uuid": null },
  "commands": [
    {
      "id": "cmd_01HA0AAA",
      "command": "lp user {username} parent add vip",
      "delivery": "del_01HA0...",
      "product": "prod_01H9Z4ABCDEF",
      "conditions": { "delay": 0, "slots": 1 }
    }
  ]
}
```

Run each `command`, substituting placeholders (such as `{username}` and
`{uuid}`) with the player's values. The queue returns commands exactly as you
wrote them on the package, placeholders included; filling them in is your job.
Since `uuid` is `null`, resolve it on your side if a command uses `{uuid}` (the
Minecraft plugin asks the game server). `conditions.slots` tells you how much
free inventory space the player needs before an item command should run.

A player id that does not belong to your store returns `404`. At most 100
commands come back per call; anything beyond that appears on the next poll.

### 3. Run offline commands

When `meta.execute_offline_commands` is `true`, fetch the batch that does not
need a connected player:

```
GET /v1/queue/offline-commands
```

```json
{
  "object": "command_list",
  "commands": [
    {
      "id": "cmd_01HA0BBB",
      "command": "eco give {username} 5000",
      "delivery": "del_01HA0...",
      "product": "prod_01H9Z4CURR",
      "conditions": { "delay": 0, "slots": 0 },
      "player": { "id": "qp_01HA0...", "name": "Steve", "uuid": null }
    }
  ],
  "more": false
}
```

Each offline command carries its own `player` block, since there is no
per-player fetch step. Up to 100 commands come back per call; `more: true`
means there are more due, so fetch again after confirming this batch.

### 4. Confirm execution

After a command runs successfully, **delete it** so 2Pay marks its delivery
complete and never re-sends it:

```
DELETE /v1/queue
```

```bash
curl -X DELETE https://game.2pay.gg/v1/queue \
  -H "X-2Pay-Server-Token: srv_live_..." \
  -H "Content-Type: application/json" \
  -d '{"commands":["cmd_01HA0AAA","cmd_01HA0BBB"]}'
```

The response tells you how many of the ids actually moved:

```json
{ "object": "queue_confirmation", "confirmed": 2 }
```

Batch the ids of everything you ran this cycle into one call: between 1 and 500
ids per request (an empty list is refused with `400`). Ids that are unknown,
already confirmed, or queued for a different server are ignored, which is what
makes retrying a `DELETE` safe.

A package can queue several commands, and they can be spread across several servers.
The [delivery](/dev/developer-api/deliveries) is completed, and `delivery.completed`
emitted, only once **every** command it generated has been confirmed. Confirming some of
them leaves the delivery pending, which is the truthful state: the player has had part of
what they bought.

<Callout type="warn">
  Only delete a command **after** it actually ran. If you delete first and the
  command then fails, the player is charged but never receives the item, and the
  queue will not retry it. Run, verify, then delete.
</Callout>

## Command object reference

| Field | Description |
| --- | --- |
| `id` | Command id (`cmd_`). Pass this to `DELETE /queue` to confirm. |
| `command` | The string to execute, as written on the package, with any `{username}` / `{uuid}` placeholders left for you to fill in. |
| `delivery` | The `del_` id this command fulfills. |
| `product` | The product that generated it. |
| `player` | Player identity (present on offline commands; fetched separately for online). |
| `conditions.delay` | Seconds still to wait. Always `0` today: the queue withholds a delayed command until it is due, so there is nothing left to wait for. |
| `conditions.slots` | Free inventory slots required, `0` when the command needs none. Meaningful for online commands. |

## Polling cadence and retries

- Respect `meta.next_check`: it is `15` seconds while work is waiting and `60`
  when the queue is idle.
- If you cannot run a command this cycle (player has no inventory space, server is
  restarting), **do not delete it**. It stays queued and reappears next poll.
- Network failure on `DELETE`? Just send the same `DELETE` again. Confirming is
  idempotent by itself: ids that are already confirmed are ignored, so a repeat
  never double-completes a delivery. The Game API does not use the
  `Idempotency-Key` header, on `DELETE` or anywhere else; there is no stored
  response to replay.

## Server information

```
GET /v1/information
```

Returns the store and server this token is bound to, handy for a plugin to show
which account it is connected to:

```json
{
  "object": "server_information",
  "server": { "id": "srv_01HA0...", "name": "Survival" },
  "store": { "id": "str_01H9Z...", "name": "My Store", "currency": "eur" }
}
```

## Rate limits

Every Game API endpoint allows **120 requests per minute**. The limit is
counted per endpoint and per server token, so several servers polling from one
machine or behind one NAT each get their own budget. Polling at
`meta.next_check` stays far below it.

Over the limit you get `429` with `code: "rate_limit_exceeded"` and a
`Retry-After` header in seconds. Every response carries `X-RateLimit-Limit`,
`X-RateLimit-Remaining` and `X-RateLimit-Reset`.
