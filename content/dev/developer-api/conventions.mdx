Every endpoint in the Developer API follows the rules on this page. Learn them
once and they hold everywhere.

## Base URL and versioning

```
https://api.ipago.io/v1
```

The major version is pinned in the path (`/v1`). New fields and endpoints are
added without changing it, so write tolerant parsers: **ignore fields you do not
recognize** rather than failing on them.

## Requests

- Send request bodies as **JSON** with `Content-Type: application/json`. Form
  encoding (`application/x-www-form-urlencoded`) is refused with `415 unsupported_media_type`.
- Query parameters are plain strings, for example `?status=paid&limit=50`.
- Authenticate with a bearer key on every request (see
  [Authentication](/dev/developer-api/authentication)).

```bash
curl https://api.ipago.io/v1/refunds \
  -H "Authorization: Bearer sk_live_..." \
  -H "Content-Type: application/json" \
  -d '{ "order": "ord_01M5MWDACTVABBZT3E8T2B6QA5" }'
```

## Responses and object types

Responses are JSON. Every resource includes an `object` field naming its type:

```json
{
  "object": "product",
  "id": "prod_01M5MWCZPX3X7V41C1J6Y83TGW",
  "name": "VIP Rank"
}
```

This lets you write one dispatch path keyed on `object`, which is especially
handy for [events](/dev/developer-api/events) and webhook payloads.

## IDs

Identifiers are a type prefix, an underscore, and a 26-character
[ULID](https://github.com/ulid/spec). Treat the whole string as an opaque token;
never parse meaning out of the part after the prefix.

| Prefix | Resource |
| --- | --- |
| `prod_` | Product |
| `cat_` | Category |
| `ord_` | Order (also the `id` of a checkout) |
| `oi_` | Order line item |
| `del_` | Delivery |
| `re_` | Refund |
| `po_` | Payout |
| `dp_` | Dispute |
| `le_` | Ledger entry |
| `ltx_` | Ledger transaction |
| `evt_` | Event |
| `we_` | Webhook endpoint |
| `sub_` | Subscription |
| `bskt_` | Storefront basket |

## Money

Monetary amounts are an **integer in the currency's minor unit** plus an ISO 4217
`currency` code in lowercase. There are no floating-point amounts anywhere in the
API.

```json
{ "amount": 999, "currency": "eur" }
```

That is `9.99 EUR`. Some objects (refunds, payouts, disputes, ledger entries)
carry `amount` and `currency` as two top-level fields instead of a nested object;
the units are the same.

## Timestamps

All times are **ISO 8601 strings in UTC**, for example
`2026-10-23T17:19:42.212Z`. There are no Unix-epoch integers in responses.

## Pagination

List endpoints return at most `limit` items (default `20`, max `100`) in a list
envelope and page with `starting_after` / `ending_before` cursors. See
[Pagination](/dev/developer-api/pagination).

## Idempotency

`POST /v1/checkouts`, `POST /v1/refunds`, `POST /v1/payouts`, and
`POST /v1/webhook_endpoints` accept an **`Idempotency-Key`** header so a retry
never repeats the action. See [Idempotency](/dev/developer-api/idempotency).

## Errors

Failures use a standard HTTP status code plus a JSON body with a single `error`
object:

```json
{
  "error": {
    "type": "invalid_request_error",
    "code": "validation_error",
    "message": "body/items Too small: expected array to have >=1 items",
    "param": "items",
    "request_id": "req_a9cb6e6e-2d08-4171-be59-9db7346a7cdf"
  }
}
```

Branch on `error.code`, never on `message`. The full list of fields, types, and
status codes is on [Errors](/dev/developer-api/errors).

## Rate limits

Requests are rate limited per key, and every response reports your remaining
budget in `x-ratelimit-*` headers. See [Rate limits](/dev/developer-api/rate-limits).

## Request IDs

Every error body includes a `request_id` (for example `req_a9cb6e6e-...`). Log
it. When something looks wrong, quoting the `request_id` lets us find the exact
request.
