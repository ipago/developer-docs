Every HTTP endpoint in the Developer API (and the [Affiliate API](/dev/affiliate-api/overview),
which shares this surface) follows the rules on this page. Learn them once and
they hold everywhere.

## Base URL and versioning

```
https://api.2pay.gg/v1
```

The major version is pinned in the path (`/v1`). We add new fields and new
endpoints without bumping it, so write tolerant parsers: **ignore fields you do
not recognize** rather than failing on them. A breaking change would ship under a
new path (`/v2`) with prior notice; it would never silently change `/v1`.

All traffic is HTTPS. Plain HTTP requests are rejected.

## Requests

- Send bodies as `application/x-www-form-urlencoded` or `application/json`; both
  are accepted on writes.
- Nested fields use bracket notation in form bodies, for example
  `items[0][product]=prod_...`.
- Authenticate with a bearer key on every request (see
  [Authentication](/dev/developer-api/authentication)).

## Responses and object types

Responses are JSON. Every resource includes an `object` field naming its type:

```json
{
  "object": "product",
  "id": "prod_01H9Z4...",
  "name": "VIP Rank"
}
```

This lets you write one dispatch path keyed on `object`, which is especially
handy for [events](/dev/developer-api/events) and webhook payloads.

## IDs

Identifiers are opaque, URL-safe strings with a type prefix. Never parse meaning
out of the part after the prefix; treat the whole string as a token.

| Prefix | Resource |
| --- | --- |
| `prod_` | Product |
| `cat_` | Category |
| `ord_` | Order |
| `dlv_` | Delivery (a line item's fulfillment) |
| `evt_` | Event |
| `we_` | Webhook endpoint |
| `chk_` | Checkout |
| `aff_` | Affiliate |
| `ref_` | Referral |
| `com_` | Commission |

## Money

Monetary amounts are an **integer in the currency's minor unit** plus an ISO 4217
`currency` code in lowercase. There are no floating-point amounts anywhere in the
API, which avoids rounding drift.

```json
{ "amount": 999, "currency": "eur" }
```

That is `9.99 EUR`. For zero-decimal currencies such as JPY, the minor unit is
the whole unit, so `500` is `500 JPY`.

## Timestamps

All times are **RFC 3339 / ISO 8601 strings in UTC**, for example
`2026-06-28T11:42:09Z`. There are no Unix-epoch integers in responses.

## Pagination

List endpoints are **cursor-based**. They return at most `limit` items (default
`20`, max `100`) wrapped in a list envelope:

```json
{
  "object": "list",
  "data": [ { "object": "order", "id": "ord_03..." } ],
  "has_more": true
}
```

To page forward, pass the last id you saw as `starting_after`:

```bash
curl "https://api.2pay.gg/v1/orders?limit=50&starting_after=ord_03..." \
  -H "Authorization: Bearer sk_live_..."
```

Keep requesting until `has_more` is `false`. Cursors are stable under inserts, so
you will not skip or double-read rows that change mid-iteration. Use
`ending_before` to page backward.

## Idempotency

Every `POST` accepts an **`Idempotency-Key`** header: a unique value you generate
(a UUID is ideal). If a request is interrupted and you retry with the same key,
2Pay returns the original result instead of performing the action twice.

```bash
curl -X POST https://api.2pay.gg/v1/deliveries/dlv_01.../complete \
  -H "Authorization: Bearer sk_live_..." \
  -H "Idempotency-Key: 0d5a1f2e-..."
```

Keys are retained for **24 hours**. Reuse the same key only for a retry of the
exact same request; reusing it for a different payload returns an error.

<Callout type="info">
  Always send an idempotency key on writes. Network timeouts are the normal
  case, not the exception, and retrying safely is the whole point.
</Callout>

## Errors

Failures use a standard HTTP status code plus a JSON body with a single `error`
object:

```json
{
  "error": {
    "type": "invalid_request_error",
    "code": "parameter_missing",
    "message": "Missing required parameter: items.",
    "param": "items",
    "request_id": "req_01HA0..."
  }
}
```

| Field | Meaning |
| --- | --- |
| `type` | Broad class: `invalid_request_error`, `authentication_error`, `permission_error`, `rate_limit_error`, `api_error`. |
| `code` | Stable, machine-readable reason. Branch on this. |
| `message` | Human-readable explanation. Do not pattern-match on it. |
| `param` | The offending parameter, when applicable. |
| `request_id` | Identifier for this request. Include it when contacting support. |

### Status codes

| Status | Meaning |
| --- | --- |
| `200` | Success. |
| `201` | A resource was created. |
| `400` | Malformed request (bad JSON, wrong type). |
| `401` | Missing or invalid key. |
| `403` | Valid key without the required scope. |
| `404` | No such resource, or not visible to this key. |
| `409` | Conflict (for example, confirming an already-completed delivery). |
| `422` | Well-formed but semantically invalid. |
| `429` | Rate limited, see below. |
| `5xx` | Something failed on our side; safe to retry idempotent calls. |

## Rate limits

Requests are rate limited per key. Each response carries your current budget:

| Header | Meaning |
| --- | --- |
| `RateLimit-Limit` | Requests allowed in the current window. |
| `RateLimit-Remaining` | Requests left in this window. |
| `RateLimit-Reset` | Seconds until the window resets. |

On a `429`, back off and retry after `RateLimit-Reset` seconds. Use exponential
backoff with jitter for repeated `429`s or `5xx`s.

## Request IDs

Every response includes a `request_id` (also echoed in the `X-Request-Id`
header). Log it. When something looks wrong, quoting the `request_id` lets us
find the exact request instantly.
