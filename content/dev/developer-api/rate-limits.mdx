---
title: Rate limits
description: How 2Pay rate-limits the API and how to back off cleanly.
---

The Developer API is rate-limited per API key, so one integration's traffic never
eats another's budget. Limits are a backstop against runaway loops, not a quota
you are expected to plan around: normal integrations never reach them.

## The limits

Every endpoint you call with an API key uses one of two budgets, counted per key
over a one-minute window:

| Requests | Limit |
| --- | --- |
| Reads (`GET`) | 300 per minute, per key and endpoint |
| Writes (`POST`, `DELETE`) | 60 per minute, per key and endpoint |

Each endpoint keeps its own counter, so a burst of `GET /v1/orders` does not use
up your budget for `GET /v1/products`.

Other surfaces are limited separately and by client IP address rather than by
key:

| Surface | Limit |
| --- | --- |
| [Game API](/dev/game-api/overview) queue endpoints | 120 per minute |
| Public storefront reads | 120 per minute |
| Storefront basket reads | 120 per minute |
| Storefront basket changes and checkout | 20 per minute |

## What you get back

Every rate-limited response carries your current budget, so you never have to
guess:

| Header | Meaning |
| --- | --- |
| `x-ratelimit-limit` | Requests allowed in the current window. |
| `x-ratelimit-remaining` | Requests left in it. |
| `x-ratelimit-reset` | Seconds until the window resets. |
| `retry-after` | On a `429`, seconds to wait before retrying. |

When you exceed a limit the API responds with `429` and a `rate_limit_error`:

```json
{
  "error": {
    "type": "rate_limit_error",
    "code": "rate_limit_exceeded",
    "message": "Rate limit exceeded, retry in 1 minute",
    "request_id": "req_..."
  }
}
```

## Backing off

- Retry `429` responses with **exponential backoff and jitter**, not a tight loop.
  Honour `retry-after` when it is present.
- Cache catalog reads (products, categories) rather than fetching them per page
  view. The catalog changes rarely, so a short local cache removes most traffic.
- Prefer [webhooks](/dev/webhooks/overview) over polling for order and delivery
  state. Reacting to an event is both faster and lighter than a poll loop.
