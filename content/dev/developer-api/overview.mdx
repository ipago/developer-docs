The **Developer API** is the headless, server-to-server HTTP interface for your
store. It is how your own backend reads what you sell, watches what gets bought,
confirms that buyers received what they paid for, and stays in sync with 2Pay.

It is built to be predictable: resource-oriented URLs, JSON request and response
bodies, standard HTTP verbs and status codes, bearer-token auth, and the same
conventions on every endpoint.

## What you can do with it

- **Read your catalog.** List and fetch the products and categories that you
  configured in the panel, including prices, availability, and metadata.
- **Track sales.** List and fetch orders, inspect their status, line items,
  customer, totals, and fees.
- **Manage delivery.** See which line items are delivered, pending, or failed,
  and confirm a delivery once your system has granted it.
- **Stay in sync.** Read the immutable event log and register webhook endpoints
  so 2Pay pushes changes to you instead of you polling.

## Scope

This API is intentionally narrow. It manages and observes a store whose
**products are defined in the panel**, it is not a toolkit for inventing
products or building checkouts in code.

**In scope today**

- Reading products and categories.
- Reading orders and their line items.
- Reading and confirming deliveries.
- Reading the event log and managing webhook endpoints.
- Creating a checkout that references existing products (see
  [Checkout](/dev/checkout/overview)).

**Deliberately out of scope, for now**

- **Creating ad-hoc products in the request body.** Products live in the panel;
  the API references them by `id`. (This is the main thing we do differently from
  Tebex's "Checkout API" pattern.)
- **Editing pricing, themes, or store configuration.** Those are panel
  operations.
- **Baskets, subscriptions, refunds, payouts, and coupons as public write
  endpoints.** These exist in the platform but are not part of the public API
  surface yet.

<Callout type="info">
  Some of these may open up over time. If a missing endpoint is blocking you,
  tell us at [support@2pay.gg](mailto:support@2pay.gg), real use cases drive what
  we expose next.
</Callout>

## The shape of a request

Every call is an HTTPS request to `https://api.2pay.gg/v1` carrying a secret key
as a bearer token:

```bash
curl https://api.2pay.gg/v1/products \
  -H "Authorization: Bearer sk_live_..."
```

Responses are JSON. Single resources carry an `object` field naming their type;
lists wrap their results in a `{ "object": "list", "data": [...], "has_more": ... }`
envelope.
