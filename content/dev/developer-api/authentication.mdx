---
title: Authentication
description: API keys, test and live mode, scopes, and how to keep secrets safe.
---

The Developer API authenticates with **secret API keys** passed as a bearer
token. There are no signed query strings and no session cookies, just a key in a
header on every request.

```bash
curl https://api.2pay.io/v1/orders \
  -H "Authorization: Bearer sk_live_..."
```

A request without a valid key fails with `401 Unauthorized`; a request whose key
lacks the required scope fails with `403 Forbidden`.

## Key types

| Prefix | Mode | Use it for |
| --- | --- | --- |
| `sk_test_` | Test / sandbox | Building and automated tests. No real money moves. |
| `sk_live_` | Live | Your real store and real payouts. |

Test and live keys address two completely separate datasets. A `prod_...` id
created in live mode does not exist in test mode, and vice versa. This lets you
develop against a realistic copy of your store without touching production.

<Callout type="warn">
  Secret keys can read your sales and act on your store. Treat them like
  passwords: keep them server-side, store them in a secrets manager or
  environment variable, never commit them, and never ship them in a browser
  bundle, mobile app, or anything a customer can open.
</Callout>

## Scopes

A key carries a set of **scopes** that bound what it can do. Grant the least a
key needs:

| Scope | Grants |
| --- | --- |
| `products:read` | List and fetch products and categories. |
| `orders:read` | List and fetch orders and their line items. |
| `deliveries:read` | Read delivery state. |
| `deliveries:write` | Confirm or fail a delivery. |
| `checkouts:write` | Create checkouts that reference existing products. |
| `events:read` | Read the event log. |
| `webhooks:write` | Create and delete webhook endpoints. |

A read-only reporting job, for example, should hold only `orders:read` and
`products:read`, even a leaked copy could then do no harm beyond reading.

## Creating and rotating keys

Create keys in the panel under **Developers → API keys**. The full secret is
shown **once, at creation**; store it immediately, because it cannot be
retrieved again afterward (you would create a new one instead).

To rotate a key without downtime:

1. Create a second key with the same scopes.
2. Deploy it to your services.
3. Confirm traffic is flowing on the new key.
4. Revoke the old key.

Revoking is instant: the next request using a revoked key gets `401`.

## The authenticated account

A key acts on the **store it was created for**. You do not pass an account
identifier in the URL; the key resolves to its store. If you operate more than
one store, use a separate key per store.

## Errors

| Status | Meaning | Likely cause |
| --- | --- | --- |
| `401 Unauthorized` | No key, or an invalid/revoked key. | Missing header, typo, or rotated-out key. |
| `403 Forbidden` | Valid key, missing scope. | The key lacks the scope the endpoint needs. |

Both follow the standard [error shape](/dev/developer-api/conventions#errors),
so you can branch on `error.code` programmatically.
