title: Authentication
description: API keys, test and live mode, scopes, and how to keep secrets safe.
---

The Developer API authenticates with **secret API keys** passed as a bearer
token. There are no signed query strings and no session cookies, just a key in a
header on every request.

```bash
curl https://api.ipago.io/v1/orders \
  -H "Authorization: Bearer sk_live_..."
```

A request without a valid key fails with `401`; a request whose key lacks the
required scope fails with `403`.

## Key modes

| Prefix | Mode | Use it for |
| --- | --- | --- |
| `sk_test_` | Test | Building and automated tests. No real money moves. |
| `sk_live_` | Live | Your real store, live sales, and the current `/v1/payouts` routes. |

Test and live keys address two completely separate datasets. A `prod_...` id
created in live mode does not exist in test mode, and vice versa. See
[Test mode](/dev/developer-api/test-mode) for what the sandbox covers.

<Callout type="warn">
  Secret keys can read your sales and move money. Treat them like passwords: keep
  them server-side, store them in a secrets manager or environment variable,
  never commit them, and never ship them in a browser bundle, mobile app, or
  anything a customer can open.
</Callout>

## Scopes

A key carries a set of **scopes** that bound what it can do. Grant the least a
key needs:

| Scope | Grants |
| --- | --- |
| `products:read` | List and fetch products and categories. |
| `orders:read` | List and fetch orders. |
| `checkouts:write` | Create checkouts for existing products. |
| `deliveries:read` | List and fetch deliveries. |
| `deliveries:write` | Mark a delivery completed or failed. |
| `refunds:read` | List and fetch refunds. |
| `refunds:write` | Refund an order. |
| `payouts:read` | List and fetch `payout` objects (`GET /v1/payouts`). The name stays until the ledger change. |
| `payouts:write` | Call `POST /v1/payouts`. Supplier settlement is the weekly invoice, not this scope. |
| `ledger:read` | Read `GET /v1/balance` and ledger entries. The path stays until the ledger change. |
| `disputes:read` | List and fetch disputes. |
| `events:read` | List and fetch events. |
| `webhooks:read` | List and fetch webhook endpoints. |
| `webhooks:write` | Create and delete webhook endpoints, and send a test event. |

A read-only reporting job, for example, should hold only `orders:read` and
`products:read`, so even a leaked copy could do no harm beyond reading. Be
especially careful with `refunds:write` and `payouts:write`, which move money.

## Creating and rotating keys

Create keys in the panel under **Integration → Webhooks and Custom API**, in the
**Developer API** section. Only store owners and admins can create and revoke
keys. Switch the page to Test or Live first: a key belongs to the mode it was
created in.

The full secret is shown **once, at creation**. Store it immediately; afterwards
the panel only shows a masked form such as `sk_live_...a1b2`, and you would
create a new key instead.

To rotate a key without downtime:

1. Create a second key with the same scopes.
2. Deploy it to your services.
3. Confirm traffic is flowing on the new key.
4. Revoke the old key.

Revoking is immediate: the next request using a revoked key gets `401`.

## The authenticated store

A key acts on the **store and mode it was created for**. You do not pass a store
identifier in the URL; the key resolves to its store. If you operate more than
one store, use a separate key per store.

## Errors

| Status | `code` | Likely cause |
| --- | --- | --- |
| `401` | `missing_api_key` | No `Authorization: Bearer ...` header. |
| `401` | `invalid_api_key` | Typo, wrong key, or a revoked key. |
| `403` | `insufficient_scope` | The key lacks the scope the endpoint needs. |

All follow the standard [error shape](/dev/developer-api/errors), so you can
branch on `error.code` programmatically.
