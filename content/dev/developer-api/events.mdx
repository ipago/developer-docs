title: Events
description: The immutable log of everything that happened, and the source behind webhooks.
---

An **event** is an immutable record that something happened in your store: an
order was paid, a delivery completed, a refund landed. Every
[webhook](/dev/webhooks/overview) 2Pay sends is the same event object, just
pushed to your endpoint instead of pulled from this log.

The event log is your safety net. If your webhook endpoint was down, or you want
to replay history, you read events here.

## The event object

```json
{
  "object": "event",
  "id": "evt_01HA0ABC",
  "type": "order.paid",
  "created": "2026-06-28T11:42:11Z",
  "data": {
    "object": "order",
    "id": "ord_01HA0XYZ",
    "status": "paid"
  }
}
```

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Event id (`evt_`). Stable; use it to deduplicate. |
| `type` | string | What happened, see [event types](#event-types). |
| `created` | string | When the event was generated (RFC 3339 UTC). |
| `data.object` | object | The resource the event is about, in the same shape the API returns it. |

The `data.object` always carries an `object` field, so you can dispatch on
`event.type` and then trust the nested object's type.

## Event types

These are the events you can subscribe to and read. They map one-to-one to the
webhook events in [Webhooks → Events](/dev/webhooks/events).

| Type | Fires when | `data.object` |
| --- | --- | --- |
| `order.paid` | A buyer completes payment. | `order` |
| `order.refunded` | An order is fully or partially refunded. | `order` |
| `order.disputed` | A chargeback or dispute opens. | `order` |
| `delivery.pending` | A paid item is awaiting fulfillment. | `delivery` |
| `delivery.completed` | A delivery is confirmed complete. | `delivery` |
| `delivery.failed` | A delivery attempt fails. | `delivery` |
| `product.created` | A new product is added in the panel. | `product` |
| `product.updated` | A product's details change. | `product` |
| `referral.created` | A referred sale is attributed to an affiliate. | `referral` |

<Callout type="info">
  We add new event types over time. Treat an unrecognized `type` as a no-op
  rather than an error, so a new event never breaks your consumer.
</Callout>

## List events

```
GET /v1/events
```

**Query parameters**

| Parameter | Description |
| --- | --- |
| `type` | Filter to one event type. |
| `created[gte]` / `created[lte]` | Time-range filter. |
| `limit`, `starting_after`, `ending_before` | [Pagination](/dev/developer-api/conventions#pagination). |

```bash
curl "https://api.2pay.gg/v1/events?type=order.paid&limit=100" \
  -H "Authorization: Bearer sk_live_..."
```

## Retrieve an event

```
GET /v1/events/{id}
```

## Retention

Events are retained for **30 days**. For anything you need permanently, persist
the relevant data in your own store as you process each event, do not treat this
log as long-term storage.

## Catching up after downtime

If your webhook consumer was offline, do not wait for retries to trickle in.
Instead, pull the gap directly:

```bash
curl "https://api.2pay.gg/v1/events?created[gte]=2026-06-28T09:00:00Z" \
  -H "Authorization: Bearer sk_live_..."
```

Process each event, deduplicating by `event.id` against what you have already
handled. Because event ids are stable and your handlers should be idempotent,
replaying an event you already processed is harmless.
