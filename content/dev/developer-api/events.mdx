title: Events

An **event** is an immutable record that something happened in your store: an
order was paid, a delivery completed, a payout landed. Every
[webhook](/dev/webhooks/overview) iPago sends is the same event object, just
pushed to your endpoint instead of pulled from this log.

The event log is your safety net. If your webhook endpoint was down, you read the
events you missed here.

Requires the `events:read` scope.

## The event object

```json
{
  "object": "event",
  "id": "evt_01M5MWF2T4C0J8B7K2Q9X1VZ3N",
  "type": "delivery.completed",
  "created": "2026-10-23T17:25:40.311Z",
  "data": {
    "object": "delivery",
    "id": "del_01M5MWF2T4C0J8B7K2Q9X1VZ3P",
    "order": "ord_01M5MWDACTVABBZT3E8T2B6QA5",
    "order_item": "oi_01M5MWDACTVABBZT3E8T2B6QA4",
    "product": "prod_01M5MWCZPX3X7V41C1J6Y83TGW",
    "recipient": "Notch",
    "quantity": 1,
    "config": null,
    "status": "completed",
    "note": "Granted VIP to Notch",
    "created": "2026-10-23T17:21:05.104Z",
    "completed_at": "2026-10-23T17:25:40.309Z"
  }
}
```

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Event id (`evt_`). Stable; use it to deduplicate. |
| `type` | string | What happened, see [event types](#event-types). |
| `created` | string | When the event was generated. |
| `data` | object | The resource the event is about, in the same shape the API returns it, as it was at that moment. |

`data` carries its own `object` field, so you can dispatch on `type` and then
trust the shape of `data`.

## Event types

| Type | Fires when | `data` |
| --- | --- | --- |
| `order.paid` | A buyer completes payment. | `order` |
| `order.refunded` | An order is refunded in full. A partial refund leaves the order `paid` and sends no event. | `order` |
| `delivery.pending` | A paid line item is waiting to be fulfilled. One per line item. | `delivery` |
| `delivery.completed` | A delivery is confirmed complete. | `delivery` |
| `delivery.failed` | A delivery is marked failed. | `delivery` |
| `subscription.created` | A buyer starts a recurring plan. | `subscription` |
| `subscription.renewed` | A recurring plan bills for another period. | `subscription` |
| `subscription.payment_failed` | A renewal charge is declined. The plan is past due while it is retried. | `subscription` |
| `subscription.canceled` | A recurring plan ends and will not bill again. | `subscription` |
| `payout.created` | A payout is requested. | `payout` |
| `payout.paid` | A `payout` is marked paid. Supplier settlement is the weekly invoice, not this event. | `payout` |
| `payout.failed` | A `payout` is marked failed. The event name stays until the ledger change. | `payout` |
| `dispute.created` | A buyer's bank charges back an order. | `dispute` |
| `dispute.won` | A dispute is decided for the seller. | `dispute` |
| `dispute.lost` | A dispute is decided against the seller. | `dispute` |
| `endpoint.test` | You sent a test event to a webhook endpoint. | `{ "endpoint": "we_..." }` |

<Callout type="info">
  New event types may be added over time. Treat an unrecognized `type` as a no-op
  rather than an error, so a new event never breaks your consumer.
</Callout>

## List events

```
GET /v1/events
```

Returns every event for the key's store and mode, **oldest first**. The only
parameters are the [pagination](/dev/developer-api/pagination) ones: `limit`,
`starting_after`, and `ending_before`. There is no filter by type or date, so
filter on `type` in your own code.

```bash
curl "https://api.ipago.io/v1/events?limit=100" \
  -H "Authorization: Bearer sk_live_..."
```

## Retrieve an event

```
GET /v1/events/{id}
```

## Catching up after downtime

Because events are listed oldest first and ids increase over time, the id of the
last event you processed is a bookmark. Store it, and when your consumer comes
back, read everything after it:

```bash
curl "https://api.ipago.io/v1/events?limit=100&starting_after=evt_01M5MWF2T4C0J8B7K2Q9X1VZ3N" \
  -H "Authorization: Bearer sk_live_..."
```

Repeat with the last id of each page while `has_more` is `true`. Deduplicate by
`event.id` against what you have already handled: webhooks and this log carry the
same events, and replaying one you already processed should be harmless.

## Webhook endpoints

To have events pushed to you, register an endpoint in the panel or with
`POST /v1/webhook_endpoints` (scope `webhooks:write`). See
[Webhooks](/dev/webhooks/overview) for registering endpoints, signatures, and
retries.
