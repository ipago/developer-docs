title: Orders

An **order** is a single sale: one buyer, one payment, one or more line items.
Orders are created by 2Pay when a buyer pays through a [Webstore](/dev/webstores/overview)
or embedded [Checkout](/dev/checkout/overview). Over the API they are
**read-only**, you list them, fetch them, and read their delivery state, but you
never create or mutate an order directly.

## The order object

```json
{
  "object": "order",
  "id": "ord_01HA0XYZ",
  "status": "paid",
  "customer": {
    "email": "player@example.com",
    "name": "Alex P.",
    "country": "DE",
    "ip": "203.0.113.7"
  },
  "items": [
    {
      "object": "order_item",
      "id": "oi_01HA0...",
      "product": "prod_01H9Z4ABCDEF",
      "name": "VIP Rank",
      "quantity": 1,
      "unit_price": { "amount": 999, "currency": "eur" },
      "delivery": "dlv_01HA0..."
    }
  ],
  "totals": {
    "subtotal": { "amount": 999, "currency": "eur" },
    "tax": { "amount": 190, "currency": "eur" },
    "total": { "amount": 1189, "currency": "eur" }
  },
  "fees": {
    "platform": { "amount": 59, "currency": "eur" },
    "gateway": { "amount": 35, "currency": "eur" }
  },
  "payment_method": "paypal",
  "coupon": null,
  "referral": null,
  "delivery_status": "pending",
  "created": "2026-06-28T11:42:09Z",
  "paid_at": "2026-06-28T11:42:11Z"
}
```

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Order id (`ord_`). |
| `status` | string | Payment lifecycle, see [statuses](#statuses). |
| `customer` | object | Buyer email, name, country, and IP. |
| `items` | array | Line items, see [the line item](#line-items). |
| `totals` | object | `subtotal`, `tax`, and `total` as [money](/dev/developer-api/conventions#money). |
| `fees` | object | What 2Pay's `platform` fee and the `gateway` fee cost on this sale. |
| `payment_method` | string | Provider used, for example `paypal`, `card`, `klarna`. |
| `coupon` | string \| null | Coupon code applied, if any. |
| `referral` | string \| null | [Referral](/dev/affiliate-api/overview) id, if the sale was attributed to an affiliate. |
| `delivery_status` | string | Aggregate of all line-item deliveries: `pending`, `partial`, `completed`, or `failed`. |
| `created` | string | When the order was opened. |
| `paid_at` | string \| null | When payment completed; `null` until paid. |

### Line items

Each entry in `items` is an `order_item`:

| Field | Description |
| --- | --- |
| `id` | Line item id (`oi_`). |
| `product` | The `prod_` id this line refers to. |
| `name` | Product name captured at purchase time. |
| `quantity` | How many were bought. |
| `unit_price` | Price per unit at purchase time. |
| `delivery` | The `dlv_` id tracking this line's fulfillment. See [Deliveries](/dev/developer-api/deliveries). |

<Callout type="info">
  `name` and `unit_price` are snapshots taken when the order was placed. If you
  later rename or reprice the product in the panel, historical orders keep what
  the buyer actually saw and paid.
</Callout>

## Statuses

| `status` | Meaning |
| --- | --- |
| `pending` | Created, awaiting payment (buyer is mid-checkout). |
| `paid` | Payment completed. Delivery can begin. |
| `refunded` | Fully refunded. |
| `partially_refunded` | Part of the order was refunded. |
| `disputed` | A chargeback or dispute is open. |
| `cancelled` | Abandoned or cancelled before payment. |

Only `paid` orders should trigger fulfillment. Never deliver on `pending`.

## List orders

```
GET /v1/orders
```

**Query parameters**

| Parameter | Description |
| --- | --- |
| `status` | Filter by order status. |
| `delivery_status` | Filter by aggregate delivery state. |
| `created[gte]` / `created[lte]` | Time-range filter (RFC 3339). |
| `customer_email` | Orders for one buyer. |
| `limit`, `starting_after`, `ending_before` | [Pagination](/dev/developer-api/conventions#pagination). |

```bash
curl "https://api.2pay.io/v1/orders?status=paid&delivery_status=pending" \
  -H "Authorization: Bearer sk_live_..."
```

This particular query, paid but not yet delivered, is a useful reconciliation
sweep: run it periodically to catch anything a missed webhook left undelivered.

## Retrieve an order

```
GET /v1/orders/{id}
```

```bash
curl https://api.2pay.io/v1/orders/ord_01HA0XYZ \
  -H "Authorization: Bearer sk_live_..."
```

## Reconciliation pattern

Webhooks are your real-time signal, but treat them as a hint, not the system of
record. The robust pattern:

1. React to `order.paid` webhooks as they arrive.
2. On a schedule (say, every few minutes), run
   `GET /orders?status=paid&delivery_status=pending` and process anything your
   webhook handler missed.
3. Use the [Deliveries](/dev/developer-api/deliveries) endpoint to confirm each
   item, with an [idempotency key](/dev/developer-api/conventions#idempotency) so
   the periodic sweep never double-grants.
