---
title: Errors
description: The 2Pay error object, HTTP status codes, and error types you should handle.
---

2Pay uses conventional HTTP status codes and returns a structured error object so
your code can branch on a stable machine-readable field rather than parsing prose.

## The error object

```json
{
  "error": {
    "type": "invalid_request_error",
    "code": "resource_missing",
    "message": "No such order: ord_nope",
    "request_id": "req_faf9b1de-cefd-4cd2-9dea-0620f82341ed"
  }
}
```

| Field | Meaning |
| --- | --- |
| `type` | Broad class of error, see below. |
| `code` | Stable, specific identifier for the exact problem. Branch on this. |
| `message` | Human-readable explanation. Do not pattern-match on it. |
| `param` | The offending field, when one specific field caused the error. Omitted otherwise. |
| `request_id` | Identifier for this request. Include it when contacting support. |

## Error types

| `type` | HTTP | Meaning |
| --- | --- | --- |
| `invalid_request_error` | 400 / 404 / 409 | The request was malformed, referenced something that does not exist, or conflicted with current state. |
| `authentication_error` | 401 | The API key is missing, invalid, or revoked. |
| `permission_error` | 403 | The key is valid but lacks the scope, or the store or account is not allowed to do this yet. |
| `rate_limit_error` | 429 | Too many requests. See [Rate limits](/dev/developer-api/rate-limits). |
| `api_error` | 500 / 503 | Something went wrong on our side, or a dependency is unavailable. |

## Common codes

| Status | `code` | Meaning |
| --- | --- | --- |
| `400` | `validation_error` | The body or query did not match the endpoint's schema (for example `limit=500`). `param` names the field when there is one. |
| `400` | `invalid_json` | The body is not valid JSON. |
| `415` | `unsupported_media_type` | The body was not sent as `application/json` (for example form encoding). |
| `413` | `body_too_large` | The body is larger than the API accepts. |
| `400` | `invalid_cursor` | Both `starting_after` and `ending_before` were sent, or a cursor was empty. |
| `401` | `missing_api_key` / `invalid_api_key` | See [Authentication](/dev/developer-api/authentication#errors). |
| `403` | `insufficient_scope` | The key lacks the scope this endpoint needs. |
| `404` | `resource_missing` | No such object in this store and mode. |
| `404` | `unknown_route` | The method and path do not exist. |
| `409` | `idempotency_key_reuse` | The `Idempotency-Key` was already used for a different request. |
| `429` | `rate_limit_exceeded` | Slow down, see [Rate limits](/dev/developer-api/rate-limits). |
| `500` | `internal_error` | An unexpected failure on our side. |

Endpoint-specific codes, such as `order_not_refundable` or
`insufficient_balance`, are listed on each endpoint's page.

<Callout type="info">
  Objects that belong to another store, or to the other mode, return `404
  resource_missing`, never `403`. The API does not reveal whether an id exists
  somewhere you cannot see.
</Callout>

## Handling errors

Treat `4xx` as caller mistakes to fix, and `5xx` (plus `429`) as transient.
Retry `5xx` and `429` with backoff, and send an
[Idempotency-Key](/dev/developer-api/idempotency) on the endpoints that accept
one so a retry never repeats an action. Do not retry a `4xx` without changing the
request.
