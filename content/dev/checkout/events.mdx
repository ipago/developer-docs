The widget has no event emitter and no `on(...)` API. It reports back through
the callbacks you pass to `mount`:

| Callback | When it is called |
| --- | --- |
| `createSession(values)` | The buyer submitted the form and every required field is filled. |
| `onError(error)` | `createSession` threw or returned no `clientSecret`, or the payment form failed to load. |
| `onComplete(result)` | Never, in the current version. It is part of the options type so the contract stays stable, but nothing calls it yet. |

```js
mount({
  element: "#checkout",
  publishableKey,
  fields,
  createSession,
  onError: (err) => showToast(`Checkout failed: ${err.message}`),
});
```

## How a payment completes

When the buyer pays, the embedded checkout redirects them to the `return_url`
your server set on [`POST /v1/checkouts`](/dev/checkout/integrating#1-create-a-checkout-server-side)
(or to 2Pay's hosted confirmation page if you set none). Put
`{CHECKOUT_SESSION_ID}` in the URL if your return page needs the session id.

Your return page is for showing the buyer a thank-you message. It is not proof of
payment: a buyer can open that URL without paying.

## Fulfil from webhooks

<Callout type="warn">
  Never grant a purchase from the browser. Fulfilment must be driven by the
  [`order.paid` webhook](/dev/webhooks/events), which is signed, retried, and
  server-to-server.
</Callout>

| Concern | Source of truth |
| --- | --- |
| Updating the buyer's UI | The widget callbacks and your return page. |
| Granting items, ranks, keys, roles | The `order.paid` webhook and the [Deliveries API](/dev/developer-api/deliveries). |
