<Callout type="warn">Preview: the drop-in overlay described on this page (a script tag, an `ident`, `launch()`) is the planned shape. What ships today is a mountable payment form you embed yourself, and it is what [Integrating](/dev/checkout/integrating) documents.</Callout>

**Checkout** lets you drop the 2Pay payment experience straight into your own
website or app. The buyer pays in an overlay on your page instead of being sent
off to a separate domain, which keeps your branding intact and lifts conversion.
It is 2Pay's drop-in checkout library: you load a small script, hand it a checkout
identifier, and it renders the whole payment flow.

Under the hood, 2Pay still acts as [Merchant of Record](/dev/index): the library
collects payment, and 2Pay settles it, handles tax, and screens fraud. You write
no payment code and never touch card data.

## Products come first

Checkout sells the products you have **already defined in the panel at
[app.2pay.gg](https://app.2pay.gg)**. It references those products by id; it does
**not** create products on the fly. This is the key difference from an "ad-hoc
product" checkout API: your catalog stays the single source of truth.

## The shape of an integration

A Checkout integration has two halves, and the split matters for security:

1. **Server side.** Your backend calls the
   [Developer API](/dev/developer-api/overview) to create a *checkout* for the
   products the buyer chose. This returns a short-lived `client_secret`. This step
   uses your secret key, so it must happen on your server, never in the browser.
2. **Client side.** Your frontend loads the 2Pay browser library, passes it the
   `ident`, and launches the overlay. No secret key is exposed; the `ident` is a
   one-time handle to a checkout your server already authorized.

```
Browser                         Your server                 2Pay
  │  "buy VIP Rank"  ─────────────▶ │                          │
  │                                 │ POST /v1/checkouts ─────▶ │
  │                                 │ ◀───── { ident } ─────────│
  │  ◀──────── ident ───────────────│                          │
  │  Tebex-style: launch(ident) ──────────────────────────────▶│  (overlay)
  │                              buyer pays in overlay          │
  │  ◀───── payment:complete event ────────────────────────────│
                                  (confirm via webhook, server side)
```

## When to use Checkout

Reach for Checkout when you already have your own website, game launcher, or app
and want the purchase to complete **there**, while still letting 2Pay own
payments and compliance. If you would rather not build a frontend at all, use a
hosted [Webstore](/dev/webstores/overview) instead.

## Confirm payments server-side, always

The client-side [`payment:complete`](/dev/checkout/events) event is for updating
your UI, not for granting entitlements. A closed tab or a spoofed call could lie.
Treat the [`order.paid` webhook](/dev/webhooks/events) as the only source of
truth for fulfillment.
