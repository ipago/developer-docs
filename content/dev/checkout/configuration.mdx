The widget has a single entry point, `mount(options)`. It returns
`{ unmount }`, which removes the form or the payment checkout, whichever is
showing.

## Options

| Option | Type | Required | Description |
| --- | --- | --- | --- |
| `element` | `string \| HTMLElement` | yes | A CSS selector or an element to render into. A selector that matches nothing throws `iPago Checkout: element not found`. |
| `fields` | `Field[]` | yes | The inputs to collect before payment, in order. |
| `createSession` | `(values) => Promise<{ clientSecret: string }>` | yes | Called with the submitted values as a `Record<string, string>`. Must resolve to `{ clientSecret }` from your server. |
| `publishableKey` | `string` | yes | The payment provider's public key for iPago's account. |
| `onError` | `(error: Error) => void` | no | Called when `createSession` throws or returns no `clientSecret`, or the payment form fails to load. Without it, errors go to `console.error`. |
| `onComplete` | `(result: { sessionId?: string }) => void` | no | Accepted but **not called** in the current version. See [Events](/dev/checkout/events). |

There are no theme, colour, or locale options. The payment step is the payment
provider's embedded checkout, which follows its own styling and the buyer's
browser language.

## Fields

`fields` is your own list. The widget does not interpret the values: it only
checks that `required` fields are not blank, then passes everything to
`createSession`. Your server maps them to the
[`POST /v1/checkouts`](/dev/checkout/integrating#1-create-a-checkout-server-side)
body, for example `username` to `delivery_target` and `email` to
`customer_email`.

Text, email, or number input:

```ts
{
  key: string;
  label: string;
  type: "text" | "email" | "number";
  required?: boolean;
  placeholder?: string;
}
```

Select:

```ts
{
  key: string;
  label: string;
  type: "select";
  required?: boolean;
  options: { value: string; label: string }[];
}
```

## What it renders

The form is plain, unstyled HTML, so your page's CSS controls its look:

- a `<form class="ipago-form">`,
- one `<div class="ipago-field">` per field, holding a `<label>` and an
  `<input>` or `<select>` with `id="ipago-{key}"` and `name="{key}"`,
- a submit button labelled **Continue**,
- for each blank required field, a `<span class="ipago-error">` reading
  `{label} is required`.

After a successful `createSession`, the form is removed and the payment checkout
is mounted in the same element.

## Content Security Policy

If your page sends a `Content-Security-Policy` header, allow the payment
provider's origins or the embedded checkout is blocked:

```
frame-src https://*.stripe.com;
connect-src https://api.stripe.com https://*.stripe.com;
script-src https://js.stripe.com;
```

## One checkout per purchase

Each `client_secret` is for one payment. To start another purchase, create a new
checkout on your server and mount again.
