---
title: Integrating
description: Create a checkout server-side, then mount the payment form on your page.
---

A working Checkout integration is two pieces: a backend call that creates a
checkout and returns a client secret, and the browser library that mounts the
payment form on your page.

<Callout type="warn">
  The library is not published to a registry or a CDN yet, so today you build it
  from `packages/checkout` in the monorepo. The API below is what the code
  actually does; the overlay API described in
  [Configuration](/dev/checkout/configuration) and [Events](/dev/checkout/events)
  is a planned design and is not built.
</Callout>

## 1. Create a checkout (server side)

When a buyer decides to pay, your **backend** creates a checkout that references
the products they chose. This uses your [secret key](/dev/developer-api/authentication),
so it must run on your server.

```bash
curl https://api.2pay.gg/v1/checkouts \
  -H "Authorization: Bearer sk_live_..." \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "items": [{ "product": "prod_01H9Z4ABCDEF", "quantity": 1 }],
    "customer_email": "player@example.com",
    "delivery_target": "Steve",
    "country": "PL",
    "return_url": "https://example.com/thanks"
  }'
```

| Field | Required | Description |
| --- | --- | --- |
| `items[].product` | yes | A `prod_` id from your catalog. |
| `items[].quantity` | no | Defaults to `1`. |
| `customer_email` | no | Pre-fills the buyer's email and receives the receipt. |
| `delivery_target` | no | In-game username, for products that deliver to a player. |
| `country` | no | ISO 3166-1 alpha-2 buyer country, used to compute VAT. Omit for non-taxable. |
| `return_url` | no | Where to send the buyer after payment. |

Always send an `Idempotency-Key`. Retrying a checkout without one is how a single
purchase becomes two charges.

The response carries the `client_secret` your frontend needs:

```json
{
  "object": "checkout",
  "id": "chk_01HA0...",
  "client_secret": "cs_test_..._secret_...",
  "status": "open",
  "total": { "amount": 1189, "currency": "eur" }
}
```

Return only the `client_secret` to the browser. It is scoped to this one payment
and carries no account-level power.

## 2. Mount the form (client side)

The library renders the fields you ask for, then swaps them for the payment
element once the buyer submits.

```js
import { mount } from "@2pay/checkout";

const handle = mount({
  element: "#checkout",
  publishableKey: "pk_live_...",   // your payment provider's publishable key
  fields: [
    { key: "username", label: "Minecraft username", type: "text", required: true },
    { key: "email", label: "Email", type: "email", required: true },
  ],
  createSession: async (values) => {
    // Ask YOUR backend to create the checkout. The secret key never reaches the browser.
    const res = await fetch("/api/checkout", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ product: "prod_01H9Z4ABCDEF", ...values }),
    });
    return res.json(); // { clientSecret }
  },
  onError: (err) => console.error(err),
});

// later, if you need to tear it down
handle.unmount();
```

The split matters: **the library never talks to the 2Pay API**. It knows only
your `createSession` callback and a publishable key, so a secret key can never
leak into a page.

| Option | Required | Description |
| --- | --- | --- |
| `element` | yes | A CSS selector or an `HTMLElement` to render into. |
| `publishableKey` | yes | The payment provider's publishable key. Safe in the browser. |
| `fields` | yes | The inputs to collect before payment. `text`, `email`, `number` or `select`. |
| `createSession` | yes | Called with the collected values; must return `{ clientSecret }`. |
| `onError` | no | Called when session creation or payment mounting fails. |

## Confirm the sale server-side

<Callout type="warn">
  Never grant the purchase based on the browser. Fulfil from the
  [`order.paid` webhook](/dev/webhooks/events), which is signed, retried, and
  impossible to spoof from a client. Verify it with
  `constructWebhookEvent` from `@2pay/sdk`.
</Callout>

## Testing

Create the checkout with a [test key](/dev/developer-api/authentication)
(`sk_test_...`) and the form runs in sandbox mode. Use these test cards:

| Card number | Result |
| --- | --- |
| `4242 4242 4242 4242` | Payment succeeds. |
| `4000 0000 0000 0002` | Card declined. |
| `4000 0000 0000 9995` | Insufficient funds. |

Any future expiry date and any CVC work in test mode. Test-mode checkouts emit
real `order.paid` events to your [test-mode webhook endpoints](/dev/webhooks/endpoints#test-mode-vs-live-mode),
so you can exercise the full loop without moving money.
