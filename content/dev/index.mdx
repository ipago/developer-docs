The **2Pay Developer docs** are the technical reference for wiring 2Pay into
software you already run: a website, a backend service, a game server, or a
storefront. Everything here assumes one thing about your account, so let's get it
out of the way first.

## How 2Pay is shaped

2Pay is a **Merchant of Record (MoR)**. When a buyer pays, 2Pay is the seller on
record, so 2Pay owns the parts of a sale that are painful to build yourself:
payment processing, sales tax and VAT, fraud screening, chargebacks, and your
payouts. Your integration never touches card data and never has to register for
tax in dozens of jurisdictions.

Because of that, the developer surface is split cleanly in two:

- **The panel at [app.2pay.gg](https://app.2pay.gg)** is where products,
  prices, categories, themes, and payout details are **created and
  configured**. This is the source of truth.
- **The APIs documented here** let your own systems **read** that catalog,
  **take payments** against it, **watch** what sells, **confirm** delivery,
  **move money** (refunds and payouts), and **react** to events. They are a
  synchronization and runtime layer, not a place to define new products on the
  fly.

<Callout type="info">
  If your mental model comes from Tebex: we cover the same ground (a hosted
  store, an embeddable checkout, webhooks, and a game-server delivery API), but
  we keep product creation inside the panel rather than exposing an ad-hoc
  "build a product in the request" API. See
  [Scope](/dev/developer-api/overview#scope) for what the API covers.
</Callout>

## Integrate

These are the programmatic interfaces your servers talk to.

<Cards>
  <Card title="Developer API" href="/dev/developer-api/overview">
    The headless HTTP API: read products and orders, create checkouts, confirm
    delivery, issue refunds and payouts, and read disputes and events.
  </Card>
  <Card title="Game API" href="/dev/game-api/overview">
    The runtime endpoint a game server or plugin polls to fetch and execute
    in-game deliveries, then report them complete.
  </Card>
  <Card title="Webhooks" href="/dev/webhooks/overview">
    Signed, retried event callbacks that push order, delivery, payout, and
    dispute changes to your backend the moment they happen.
  </Card>
</Cards>

## Conventions used across these docs

Every Developer API endpoint shares the same base URL, authentication scheme,
error format, pagination, and idempotency rules. Rather than repeat them on each
page, they live in one place:
[Developer API → Conventions](/dev/developer-api/conventions).
